# Worklog Skill

把今天/这周做的事情从电脑里"挖"出来，整理成结构化的工作汇报。**整个过程只读，不会动用户的任何文件。**

## 一、本 skill 的执行流程（按顺序）

1. **解析用户意图**：识别模式（daily/weekly）、项目路径过滤、交互模式（追问 vs AI 推断）
2. **并行采集数据**：调用 `scripts/collect.sh` 一次拿到 git/文件/编辑器/history 四路数据
3. **聚类与去重**：按项目分组、合并命令序列、过滤噪音、识别敏感操作、人话重写
4. **生成"今日/本周工作"清单**：按重要度排序，3-5 条，每条 15-25 字
5. **处理"明日工作"和"难点卡点"**：默认用 AskUserQuestion 追问；用户原话含"AI 推断"等关键词时改为自动推断
6. **组装最终输出**：严格使用指定格式，每段序号独立从 1 开始

## 二、触发条件

**只要命中其一就触发**：

1. "写日报""生成日报""今日工作总结"
2. "写周报""生成周报""本周工作"
3. "整理一下今天/这周做了什么"
4. "今天我干了啥""本周我做了啥"
5. "/worklog" 类调用（带或不带参数都可以）
6. "总结一下我的工作""汇报一下今天的工作"
7. 任何"汇报/整理/记录/总结自己做过的工作"的隐性意图（不一定要出现"日报""周报"字面量）

## 三、参数解析

从用户原话中识别以下三类信息。

### 1. 模式（决定时间窗口）

1. `日报` / `daily` / `d` / `今日` / `今天` → `daily`（今日 00:00 ~ 现在）
2. `周报` / `weekly` / `w` / `本周` / `这周` → `weekly`（本周一 00:00 ~ 现在）
3. 无任何参数 → 默认 `daily`

### 2. 项目路径过滤（可选）

1. 调用形式：`/worklog 日报 /path/to/A /path/to/B`
2. 路径必须存在；不存在时 warn 并跳过；全部无效则 exit 2 让用户重新指定
3. 传了路径后，`git log` 和 `find` 都只扫这些路径下的内容
4. **shell history 不受路径过滤影响**（命令可能跨项目）

### 3. 交互模式（决定"明日工作"和"难点卡点"怎么来）

1. **默认（追问模式）**：用 AskUserQuestion 给选项让用户挑
2. **AI 推断模式**：用户原话含以下任一关键词时启用——"让 AI 推断""AI 分析""你判断""你建议""让模型想想""自动分析""你看着办"

## 四、采集数据

**优先调用封装脚本**，避免在模型里手写 4 段 shell（容易踩 BSD/GNU 兼容、JSON 解析、sqlite3 依赖的坑）。

### 1. 主路径：一键调用

```bash
bash /Users/gengjian/.agents/skills/worklog/scripts/collect.sh <mode> [path1 path2 ...]
```

脚本会自动完成：

1. 扫描已知项目目录（或用户传入的路径）
2. 抓取 git 提交记录（since 今日 00:00 / 本周一 00:00）
3. `find -mtime -1`（日报）或 `-7`（周报）抓最近修改文件
4. 读 VSCode/Cursor 的 `state.vscdb` 拿最近打开
5. 读 `~/.zsh_history` / `~/.bash_history`；如果启用了 `EXTENDED_HISTORY` 就按时间戳过滤
6. 末尾输出 `=== SUMMARY ===` 段，告知哪些源可用、哪些不可用

**注意**：必须把这一个 Bash 调用跑完，**不要**再额外手写 4 个并行 find/git/sqlite 命令——脚本已经覆盖了。

### 2. 兜底：脚本不可用时

只有当 `collect.sh` 缺失或整体失败时，才退化到手动并行 4 个 Bash。详细命令见 `references/data-collection.md`。

## 五、聚类与去重

拿到原始数据后，按以下顺序处理：

1. **按项目分组**：用 git 仓库路径或文件所在目录前 2 级作为项目标识
2. **合并命令序列**：连续 3+ 条针对同一目录/同一仓库的命令 → 合并成 1 条
3. **过滤噪音命令**：`ls` `clear` `pwd` `cd ..` 单独的 `git status` 等去掉
4. **识别敏感操作**：`rm -rf` `chmod 777` `curl ... | bash` 含 `password=` `token=` `api_key=` `secret=` 的命令 → 标注 `⚠️ 敏感操作`，**只列出原行，不归入工作清单**
5. **过滤噪音文件**（完整清单见 `references/noise-patterns.md`）：构建产物、工具状态、日志、锁文件、本地配置等
6. **人话重写**：命令/提交/文件路径转成对用户/leader 可读的中文动宾短语

人话重写对照：

| 原始 | 重写为 |
|---|---|
| `git commit -m "fix(login): 修复 token 过期" src/auth/token.ts` | 修复登录模块的 token 过期问题 |
| `npm install vue@3.4.0 && npm run build` | 升级 Vue 到 3.4.0 并完成构建 |
| `python3 scripts/migrate.py` | 执行数据迁移脚本 |

## 六、生成"今日/本周工作"清单

聚类后按重要度排序：

1. 有 git commit 的（最确凿）
2. 有实质文件修改的（次确凿）
3. 有长命令链的（次之）
4. 纯命令调用但能推断意图的（最弱）

**数量约束**：3 条左右，最多 5 条。超过 5 条按重要度取前 5，剩余合并进已入选条目（**不要单列"其他"**）。

**单条写作规范**（日报是给领导/同事快速扫的，不是技术文档）：

1. 15-25 个汉字（含标点、技术名词），超了砍
2. 动词 + 关键对象 + 关键结果，不堆从句
3. 禁止"的""了""在……上""通过……来"等冗余结构
4. 项目名/组件名/命令用原文，不强行翻译不强行解释
5. 用"做 X / 修 X / 推 X / 验 X"等强动作词，不用"是否""评估""考虑"

精炼对照：

| ❌ 啰嗦 | ✅ 精炼 |
|---|---|
| dev→master→release 多次手工 push/merge，缺脚本化与 master 保护机制，发布期有漏步骤风险 | 多分支发布流程缺脚本化 |
| BaseForm/BasePopover 抽出后业务组件迁移量大，回归测试需充分 | 基线组件迁移回归覆盖不足 |
| 跟进了产品同事提出的关于 Q3 需求拆解的相关事项 | 跟进 Q3 需求拆解 |

## 七、处理"明日工作"和"难点卡点"

### 1. 默认：追问模式（模式 A）

两项各用一次 AskUserQuestion，给 4 个选项 + "其他"。

**A.1 明日工作**

```
question: "明天/下一阶段的工作重点是什么？"
header: "明日工作"
options:
  - label: "继续 X 项目（基于今天的工作推进）"
    description: "基于今日 commit / 修改的文件，自动填入项目名"
  - label: "评审/合并今日未完成的 PR"
    description: "如果今日有 commit 但未 push"
  - label: "会议/沟通为主（无具体代码任务）"
    description: "全天开会/对齐"
  - label: "其他"
    description: "自由输入"
```

**A.2 难点卡点**

```
question: "今天/本周有哪些卡点/难点/需要协助的事项？"
header: "难点卡点"
options:
  - label: "无明显卡点"
    description: "今日一切顺利"
  - label: "等待 X 的回复/审批"
    description: "依赖外部，X 自动推断为最高频的协作者"
  - label: "技术方案未定"
    description: "需要讨论/调研后再推进"
  - label: "其他"
    description: "自由输入"
```

### 2. AI 推断模式（模式 B）

触发条件：用户原话含"AI 推断""AI 分析""你判断""你建议""让模型想想""自动分析""你看着办"之一。

**不发起 AskUserQuestion**，直接基于"今日/本周工作"清单推断。

**B.1 明日工作（3 条左右，最多 5 条）**

对每条"今日工作"，按以下规则推断下一步：

1. 抽出了 X 通用组件 → 继续用 X 改造剩余业务 / 补 X 单元测试
2. 提交但未 push / 多分支手工 merge → 验证 push 后 CI / 流程脚本化
3. 修了 bug A → 回归 A 关联路径 / 排查类似 bug B
4. 性能/体验优化 → 真机/真实环境验证 / 补 benchmark
5. 写文档 / 重构 → 找 reviewer 评审 / 处理 review 意见
6. 开会 / 对齐 → 跟进会议纪要 TODO
7. 装工具 / 初始化 → 真正用工具产出内容
8. 跨多个独立项目 → 选一个聚焦，其余移到之后

**B.2 难点卡点（3 条左右，最多 5 条）**

从 4 个维度扫描"今日工作"：

1. 流程风险：重复手工操作 / 缺保护机制 / 缺 CI 拦截
2. 质量风险：大改未配测试 / 抽组件后老调用未迁移 / 优化未做对照
3. 知识风险：用了不熟工具 / 抄了未理解代码 / 新依赖未调研
4. 协作风险：等他人回复 / PR 无人 review / 会议决议未落地

**多个工作触发同一类风险时合并成一条**（如多次手工 push/merge 合并为"流程风险"一条）。如果完全没触发任何风险维度，输出"今日未发现明显卡点"。

### 3. 模式选择的回退规则

1. 模式 A 用户选"其他"且写了"你看着办"等表述 → 剩余项改用模式 B
2. 模式 B 用户明确说"按我说的来"并给了具体内容 → 覆盖自动推断项，保留另一项的自动结果

## 八、组装最终输出

### 1. 严格使用以下格式

日报：

```
本日工作：
 1. xxx
 2. yyy
 3. zzz
明日工作：
 1. ooo
 2. ppp
 3. qqq
难点卡点：
 1. aaa
 2. bbb
 3. ccc
```

周报：把"本日工作"改为"本周工作"，其余完全一致。

### 2. 格式硬性要求（每条都重要，违反即失败）

1. 冒号用全角`：`（中文冒号）
2. 序号格式` 1.`（半角空格 + 阿拉伯数字 + 半角点），不是`1.` `1、` `(1)`
3. **每段序号独立从 1 开始**：本日工作从` 1.`起，明日工作也从` 1.`起，难点卡点也从` 1.`起。**绝对不要**用全局连续编号（如本日 1-3、明日 4-6、卡点 7-9）。
4. 每条之间换行，每段之间空 1 行
5. 末尾不加分号、不加总结语、不加 emoji
6. 纯文本，**不裹代码块**（方便用户复制粘贴）

## 九、诚实声明（推荐追加）

最终输出**之后**追加一段（用 `---` 分隔），让用户知道哪些数据可信、哪些是兜底：

```
---
📊 数据采集摘要：
  ✅ git 提交：3 条（wrkj-ctut / leafy-note / ...）
  ✅ 最近修改：12 个文件
  ⚠️ shell history：未启用 EXTENDED_HISTORY，本次只能取全部最近 200 条
  ❌ 编辑器：未安装或未找到 state.vscdb
💡 一次性优化建议：在 ~/.zshrc 中加入 `setopt EXTENDED_HISTORY` 可让以后的历史命令带精确时间戳
```

## 十、异常处理

1. **一个数据源都拿不到**（全新电脑、无 git 仓库、history 为空）：不要伪造数据。告诉用户可能原因，用 AskUserQuestion 让用户口述
2. **git 不可用**：跳过 git 段，其余源继续，在摘要里标 `❌ git`
3. **sqlite3 不可用**：跳过编辑器段，提示 `brew install sqlite3`
4. **用户没回答追问**：把这两段写为` 1. （请补充）`占位
5. **EXTENDED_HISTORY 未启用**：不阻塞主流程；把全部最近 200 条命令当作"可能含今日"的源

## 十一、与其他 skill 的边界

1. **git-commit**：本 skill 只读汇总；git-commit 是写操作
2. **oh-my-claudecode:writer-memory / remember**：本 skill 不写 memory

## 十二、防御性规则（不在本 skill 范围时）

1. "把日报发到飞书/钉钉/邮件" → 告知用户手动复制
2. "加插图" → 告知用户先复制文字
3. "汇总团队成员的日报" → 告知单机数据源拿不到他人数据

## 十三、高质量示例

### 1. 典型一天（前端开发）

```
本日工作：
 1. 修复登录页 token 过期未续期问题
 2. 升级项目 Vue 依赖到 3.4.0 并完成本地构建
 3. 完成用户中心模块的 API 对接与字段映射
明日工作：
 1. 继续完成用户中心的列表分页与排序逻辑
 2. 与后端对齐新接口的字段命名
 3. 评审昨日未合入的 PR
难点卡点：
 1. token 续期在多标签页下偶现竞态，尚未复现稳定路径
 2. 等待后端返回用户中心的字段确认
 3. 暂无
```

### 2. 会议/沟通为主的一天

```
本日工作：
 1. 与产品对齐 Q3 需求优先级
 2. 参与架构评审会议，输出 3 条改进建议
 3. 协助同事排查生产环境偶发的 502 问题
明日工作：
 1. 跟进 Q3 需求拆解
 2. 整理架构评审的会议纪要
 3. 推进 502 问题的根因分析
难点卡点：
 1. Q3 资源排期与产品预期有冲突，待与 leader 对齐
```

## 十四、一次性环境优化（可选）

如果发现用户没开 EXTENDED_HISTORY，在摘要后提示一次（不要重复提示）：

```bash
# ~/.zshrc 追加：
setopt EXTENDED_HISTORY       # 历史带时间戳
setopt INC_APPEND_HISTORY     # 立即写入（不丢失会话）
setopt SHARE_HISTORY          # 多端共享
```
