# 个人开发偏好（可配置）

这是当前用户的默认工作方式。新增或调整偏好时，优先修改本文件的对应条目，不要把个人偏好散落复制到框架规则；保留简短的“适用条件”和“例外”，让模型能在不同项目中稳定取舍。

## 当前默认

- **范围模式**：默认采用最小化方案，只改完成当前目标所必需的代码、调用链和验证；不因顺手统一风格而扩大影响范围。用户明确说“彻底重构”时，切换为整体优化：基于业务场景重新选择最清晰、最易维护的实现，可删除不再需要的内部兼容层、冗余抽象和历史包袱；仍遵守用户或仓库明确保留的对外契约、数据迁移和安全要求。
- **整洁优先**：在本次改动触及的范围内，主动识别并清理已证实无调用方的冗余代码、重复逻辑、死代码、过期兼容层、无用导出、依赖、样式和测试辅助项。删除前检查动态入口、公开契约、持久化数据和发布兼容性；证据不足时不猜测删除。
- **最少真实状态**：直接从已有数据派生展示条件、统计值和标签，避免镜像状态。仅当状态代表独立用户意图、异步/动画过渡，或无法可靠派生的业务事实时，才新增状态。
- **谨慎声明**：变量必须承载可读的业务事实；函数、Hook 或 Composable 必须带来真实复用、隔离外部边界、封装不变量或明显降低局部复杂度。单次使用且简单的逻辑保持就近，不为形式上的“函数化”牺牲线性阅读。
- **按领域成组**：同一模块使用统一领域前缀，并将关联的状态、派生值、操作和处理器相邻排列。为复杂分组、业务理由、兼容保留或非直觉副作用写一行“为什么”的注释；不为自解释代码制造噪音注释。
- **对象成员排序**：在对象字面量及 `type`、`interface` 等对象结构声明中，先写数据字段、配置项和状态，再写函数属性、行为方法和回调；每一组内部仍按领域关联性排列。只有外部 API、序列化格式、框架约定或既有仓库规范要求特定顺序时才例外，不为满足此偏好改变运行时行为或公开契约。
- **交互有反馈**：优先复用项目已有的组件、token、主题和交互方案。缺失时，让可操作元素具备语义、键盘焦点和可感知的 hover/active 反馈；默认使用轻微透明度变化，非禁用的可点击区域显示 `cursor: pointer`。
- **动效克制**：展开/收起、弹窗、路由与组件切换可使用短促过渡以说明状态变化；优先现有方案，遵从 reduced-motion，避免影响性能、可访问性或任务效率。

## 冲突与更新

- 用户当前任务、产品设计规范、仓库约定、无障碍要求和公开兼容性优先于本文件。发生冲突时使用上位规则，不强行统一，并在交付中简述原因。
- 将未来新增偏好写成“偏好名称 + 默认行为 + 适用条件/例外”的条目。避免记录一次性实现细节、具体项目路径或与现有通用规则重复的长篇说明。
