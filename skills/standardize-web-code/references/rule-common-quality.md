# 契约、质量与安全

- 默认把 API 字段和状态码、路由、数据库/缓存/Cookie/localStorage 键、环境变量、序列化结构、i18n key、无障碍标签、测试选择器、公共导出和组件接口视为契约。删除兼容层前证明已结束支持。
- 在系统边界验证并规范化不可信输入；内部逻辑接收类型化的标准数据。按资源和动作分别执行认证与授权，避免仅凭客户端传来的对象 ID、角色或字段决定访问。错误映射集中在协议边界，日志保留可关联的请求上下文但绝不记录密码、Token、Cookie 或敏感个人信息。
- 环境变量由集中配置模块读取、校验、类型化；不在业务模块散落访问。
- API 返回值按白名单构造；限制分页大小、上传/请求体和昂贵查询，并为第三方请求配置超时、取消与失败语义。不要把内部错误、堆栈或机密直接返回客户端。
- UI 优先使用语义 HTML 和原生控件；交互必须可用键盘操作、焦点顺序合理且焦点可见。新增/修改表单要提供关联标签、可理解的错误提示与错误后的焦点策略；仅在原生语义不足时使用 ARIA。
- 测试覆盖可观察的用户/调用方行为、关键分支和失败路径，而非私有实现细节。控制时间、随机数、网络与外部依赖使测试可重复；快照仅用于能清晰审阅的稳定输出。
- 验证由窄到宽：格式化受影响文件、目标 Lint、类型/框架检查、聚焦测试；涉及路由、SSR、样式、配置、依赖或构建边界时再构建/集成验证。先确认命令的作用域与前置条件；不以启动长期开发服务替代检查。最后检查 `git diff --check`、工作区和 Diff，并避免将无关格式化噪音混入提交。
- 新增依赖、CI 动作或构建脚本前检查维护状态、许可、锁文件与最小权限；不要为了修格式化或类型问题升级无关依赖。涉及密钥的 CI 变更要审查来源、权限和固定版本策略。
- 无关测试失败要单独报告；不要宣称未执行的检查通过，也不要提交构建产物、覆盖率或报告，除非仓库明确要求。
