# 通用工作流

- 先确认仓库根目录、目标 workspace/应用和工作区状态，再按需读仓库文档、配置、相邻实现、调用方和测试；避免覆盖已有修改。Monorepo 中始终从目标 workspace 执行脚本，除非根脚本明确编排该检查。
- 默认按“定位 → 最小实现 → 聚焦验证 → 审计 Diff”推进。任务未要求时，不把局部需求扩大为全仓重构、目录迁移、依赖升级或格式化；确需扩大范围时，先说明可验证的收益和受影响契约。用户明确说“彻底重构”时，改为先梳理完整业务流、目标架构和对外约束，再以整体最优实现重组相关模块，不受旧的内部层次或冗余兼容代码限制。
- 以功能/领域为默认归属：共享代码必须有跨功能的稳定使用者；局部组件、类型、样式和辅助函数与其功能相邻。不要建立 `common`、`misc`、`helpers` 垃圾桶。
- 把删除作为重构的常规收尾：对本次触及范围搜索未引用的文件、导出、依赖、条件分支、样式和测试辅助项；确认动态入口、公开契约和生成配置后，直接删除已无使用者的代码与对应测试，不留下注释掉的实现或“以后可能用”的占位。
- 路由只做路径与编排；页面做路由级组合；配置只保存声明式数据；基础设施与领域逻辑分离。
- 复用已有脚本和最窄检查命令；先格式化受影响文件、再运行目标 Lint/类型检查/测试，最后按风险决定是否构建。不要启动持续运行的开发服务器充当验证，也不要把未执行的命令写成已通过。
- 提交保持原子、可审阅；沿用仓库的分支、提交信息、PR 与 CI 规则，不强加固定分支模型或提交格式。
- 复用仓库已有的 EditorConfig、Formatter、ESLint、Stylelint、TypeScript、测试和 CI 配置；缺失时提出建议，不在无授权下批量引入工具或固定规则集。
